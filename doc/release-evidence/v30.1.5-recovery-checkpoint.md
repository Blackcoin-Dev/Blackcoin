# v30.1.5 recovery restart and status checkpoint

This is focused implementation evidence, not release approval or closure of
the complete v30.1.5 roadmap.

- Wallet attachment reconciles the interval between loading saved transaction
  states and subscribing to validation notifications. Changed states are
  committed before memory publication; an unsuccessful commit prevents attach.
- Explicit exact-plan relay authorization records its plan, tip, wallet
  generation, origin, and exact witness transaction identity atomically with
  the authorization. The read-only receipt survives restart and revocation;
  reauthorization replaces it. Missing or malformed historical receipt data is
  reported as unavailable and does not reinterpret existing relay authority.
- `getpowclaimrecoveryinfo true {"page_size":100}` offers snapshot-bound flat
  records with a continuation cursor. Component headers and all nested list
  entries are individually bounded. The original non-paginated interface is
  preserved. Cursor scope includes wallet identity and classified Core state.

Focused native tests passed with warnings-as-errors builds:

- `shadow_pow_claim_pagination_tests` (three cases; 2,030 records including a
  1,007-node component, ordering, bounds, stale cursors, and 31-wallet cursor
  isolation).
- `walletload_tests/wallet_attach_reconciles_presubscription_disconnect`
  (actual disconnect, durable reload, metadata/index preservation, commit fault).
- `shadow_pow_claim_recovery_tests/managed_resolution_relay_revocation_is_durable_restriction_only`
  (receipt persistence/reload/revocation and malformed witness binding).
- Existing sign-only reuse, automatic chain-time accounting, complete legacy
  resolution metadata, and authorized manual scheduler retry cases.

Remaining qualification includes complete historical-status RPC fixtures,
multiwallet recovery-authority isolation (not merely cursor isolation), stable
action/refusal audit events, bounded repair/accounting work, exact historical
binary compatibility, GUI/platform checks, and final exact-source release gates.

## Shared claim-maintenance executor checkpoint

Claim-specific disconnect history scans and synchronous proof maintenance have
been replaced by one joined executor per wallet context. Each registered wallet
has one weakly owned, coalesced work slot. Selection is round-robin; repeated
notifications do not create an unbounded queue or additional threads. Unload
cancels and drains its slot before removal, including a racing late registration;
shutdown joins before wallet database flushing. Existing base transaction,
conflict, synthetic reward, and staking reconciliation remain unchanged.

Ten focused native cases passed (2,321 assertions): executor coalescing,
fairness, cancellation and shutdown; load-time reconciliation; branch quarantine
across reorg; root-only removal work; bounded cached repair; relay lock/generation
checks; exact authorized manual scheduler retry; tip/removal wakeups with mining
disabled and ordinary rebroadcast not due; and encrypted-wallet autostart.
The retained test target was rebuilt incrementally with warnings as errors.
Native daemon, CLI, and Qt application builds also passed. This does not substitute for
the functional, GUI, sanitizer, historical-binary, or final release gates.

## Native debug lock-check correction checkpoint

The Linux native compilation succeeded, but its lock-instrumented unit step
reported two failures. The legacy ownership fixture held the script-manager
lock while wallet flag persistence acquired the wallet lock; its twenty legacy
scopes now acquire wallet then script-manager locks, matching production import.
Claim maintenance called the inherited raw unlock on a tracked RAII lock,
leaving the debug lock stack inconsistent. It now releases both locks by scope,
then re-pins the wallet-only publication phase after checking the database
generation, candidate-state fingerprint and processed wallet tip. A changed
snapshot defers maintenance without granting input, signing or relay authority.

The independent platform successes remain intact and the sanitizer jobs were
not cancelled. A unit-test-only native debug build is being prepared because
the retained release build lacked lock-order instrumentation. Focused debug
validation of these corrections is pending at this checkpoint; no full hosted
rerun or final release is authorized by these unvalidated changes.

Targeted native debug validation subsequently passed all 79 selected cases and
4,918 assertions: the full 72-case wallet suite, legacy ownership suite, five
lock-order checker cases, and the bounded lock-free repair regression. No
deadlock-check suppression was added. The two independent hosted sanitizer
jobs remain under observation so any further failures can be collected before
the next exact-source qualification run. The failed native job on the previous
source is not reclassified as successful by this local result.

Both independent sanitizer jobs subsequently stopped at the same tracked-lock

required; the nine successful old-source jobs are retained as historical
